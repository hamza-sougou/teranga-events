- RBAC par organisation : enum `MemberRole` (`OWNER, CO_ORGANIZER, SELLER, CONTROLLER, ACCOUNTANT`), `OrganizationRolesGuard` + décorateur `@OrgRoles(...)`, flag global `users.is_super_admin`.

- **Inscription classique étendue + vérification email + flux Google en deux temps — nouveau.** `POST /auth/register` créait déjà utilisateur + organisation + membership `OWNER` (confirmé pendant l'exploration de cette passe) mais via des champs `organizationName`/`organizationSlug` explicites — **retirés** : le nom d'organisation est désormais toujours auto-généré (`"Organisation de {premier mot du nom}"`, même convention que celle déjà utilisée côté Google, réutilisée telle quelle plutôt qu'inventée en double), le slug via la même génération unique avec retry aléatoire. Nouveaux champs DTO : `passwordConfirmation` (vérifié serveur), `marketingOptIn` (booléen), `termsAccepted` (doit valoir `true` — stocké comme `terms_accepted_at`, un horodatage, pas juste un booléen, preuve de consentement à conserver).
  - **Vérification email** (compte classique uniquement — un compte Google a déjà prouvé l'email, jamais de code généré pour lui) : code à 6 chiffres (`crypto.randomInt`, jamais `Math.random`), hashé bcrypt, expiration 15 min, 5 tentatives max puis code invalidé jusqu'à renvoi. `POST /auth/verify-email`, `POST /auth/verify-email/resend` (throttle 3/5min). Colonnes directement sur `users` (pas de nouvelle table — un seul code actif à la fois). **Ne bloque pas la connexion** dans cette passe (décision argumentée, pas tranchée par défaut) : bloquer proprement aurait demandé un token restreint ou un rejet de `login()` qui recrée le problème "comment vérifier sans pouvoir se connecter", hors périmètre auth de cette session, avec un risque réel de bloquer un organisateur en plein montage d'évènement. `emailVerifiedAt` est tracké/exposé sur `GET /auth/me` mais ne gate rien pour l'instant — recommandation pour plus tard : gater `DRAFT→PUBLISHED` dessus, cohérent avec `organizations.is_verified` déjà inexploité (voir risque documenté dans `docs/INFRASTRUCTURE.md` §10).
  - **Flux Google en deux temps** (`AuthService.continueWithGoogle`, remplace `loginWithGoogle`) : identité Google déjà connue → connexion normale (`status: 'login'`) ; email déjà lié à un compte classique sans googleId → auto-lien conservé (sûr, Google a prouvé l'email) mais désormais **explicite** via `status: 'login_linked'` plutôt que silencieusement confondu avec un login normal ; identité totalement inconnue → **plus aucune création automatique d'organisation placeholder** — un jeton temporaire signé (JWT 15 min, payload `{ purpose: 'google_signup', googleId, email, fullName }`, sans `sub` donc jamais accepté comme jeton d'accès normal) est renvoyé (`status: 'signup_pending'`), à consommer via `POST /auth/google/pending` (décode/préremplissage) puis `POST /auth/google/complete` (création réelle, idempotente en cas de double soumission). Un seul point d'entrée `/auth/google` sert login et signup — le frontend n'a rien à distinguer à l'aller. `GET /auth/google/callback` redirige avec un fragment discriminé (`#status=login|login_linked|signup_pending&...`), jamais en query string.
  - **Conflits d'identité rendus explicites** : inscription classique sur un email déjà lié à un compte Google pur → 409 avec code distinct `GOOGLE_ACCOUNT_EXISTS` plutôt que le message générique précédent.
  - **Effet de bord découvert et corrigé pendant cette passe** : l'envoi du code de vérification bloquait initialement `register()` sur un aller-retour SMTP réel (Brevo, clés réelles en `.env`) — comme la quasi-totalité des fixtures e2e du projet (13 fichiers) appellent `authService.register()` pour amorcer un organisateur de test, ça ralentissait toute la suite au point de faire dépasser le timeout de transaction Prisma (5s) dans des tests sans rapport (`orders`, `payments-webhook`). Corrigé en deux temps : l'envoi est fire-and-forget (jamais attendu avant la réponse HTTP, même logique que `NotificationsService` — "ne jamais bloquer le chemin critique sur un canal externe" — mais sans passer par la table `notifications`/le job de balayage à la minute, latence incompatible avec un code à 15 min) et `EmailChannel.send` court-circuite l'envoi réseau réel sous `NODE_ENV=test` (même posture "silencieux en test" que `ThrottlerModule`). Un second effet de bord, une vraie race de production potentielle et pas seulement un artefact de test, a été trouvé au passage : la génération de slug d'organisation partage la même base pour deux personnes de même prénom (ex. deux "Amadou" concurrents) — `createOrganizerAccountAutoNamed` retry désormais une fois sur conflit avant d'abandonner.

### 21. Backend + Frontend web — Super Admin : Modération d'évènement + Suspension de compte
